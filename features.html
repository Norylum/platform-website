Ce que fait Norylum,
en détail.

Pas de liste marketing. Le détail technique de ce qui est implémenté, comment ça fonctionne, et ce qui est encore en cours.

Streaming · HTTP 206

Direct Play
sans transcodage.

Le serveur sert les fichiers vidéo tels quels, sans réencodage. Le client reçoit le flux original — codec, résolution, bitrate inchangés. C'est au client de gérer la décompression.

La lecture s'effectue par morceaux de 64 Ko via des streams asynchrones Tokio (ReaderStream + AsyncReadExt::take). Le serveur ne charge jamais un fichier entier en mémoire — l'empreinte RAM reste constante, indépendamment de la taille du fichier.

Les demandes de plage partielle (header Range: bytes=X-Y) sont gérées avec précision. Les plages invalides ou hors limites retournent 416 Range Not Satisfiable avec le header Content-Range: bytes */[taille].

Réponse standard
GET /v1/media/{id}

200 OK · Accept-Ranges: bytes
Content-Length: [taille exacte]
Content-Type: video/mp4

Lecture progressive
Range: bytes=0-1048575

206 Partial Content
Content-Range: bytes 0-1048575/42000000

Mémoire
O(1) — Constant

Chunks de 64 Ko en RAM quel que soit le fichier source.

Authentification

Argon2id.
Sessions Bearer.

Les mots de passe sont hashés avec Argon2id — l'algorithme recommandé par OWASP pour la résistance aux attaques GPU. Pas de MD5, pas de bcrypt vieillissant.

Chaque session est un token Bearer avec un cycle de vie complet : création, renouvellement, expiration. Les appareils sont enregistrés individuellement et peuvent être révoqués.

Chaque requête doit porter trois en-têtes de contexte : x-account-id, x-profile-id, x-device-id. L'absence de l'un d'eux déclenche un 401 immédiat — la politique fail-closed s'applique.

Profils & PIN

Plusieurs profils,
une seule instance.

Un compte Norylum peut gérer plusieurs profils — adultes et enfants. Chaque profil a son propre code PIN, sa propre liste d'appareils, et ses propres règles de contrôle parental.

Le contrôle parental est géré au niveau du serveur, pas du client. Un profil enfant avec x-is-child: true et x-age-rating-max: 10 ne peut pas accéder à un film noté 16+, quelle que soit l'application cliente.

Les sessions ont un cycle de vie géré : création lors du login, invalidation lors du logout, expiration automatique. L'historique de visionnage est conservé par profil.

Contrôle parental
Filtrage côté serveur

Le filtre s'applique indépendamment du client. Un profil enfant avec x-age-rating-max: 10 ne recevra jamais un média noté au-delà dans la liste GET /v1/library/media.

Progression de lecture
POST /v1/playback/progress

Chaque profil conserve sa position de lecture par média. La progression est enregistrée avec la position, la durée totale, et l'état de complétion.

Scan & indexation
POST /v1/library/scan

Déclenche l'inspection des dossiers configurés. FFprobe extrait les métadonnées techniques de chaque fichier : codec vidéo/audio, résolution, bitrate, durée, container. Les identifiants de médias sont stables une fois générés.

Stockage
SQLite en mode WAL

Write-Ahead Logging permet les lectures concurrentes sans bloquer les écritures. Base de données locale, pas de dépendance réseau externe pour les métadonnées.

Bibliothèque

FFprobe comme
source de vérité.

L'indexation repose sur FFprobe pour l'extraction des métadonnées techniques. Pas d'hypothèses sur les fichiers — Norylum lit ce que FFprobe dit.

L'organisation films/séries repose sur l'analyse des noms de fichiers. Les séries sont regroupées par saison et épisode, les films sont identifiés par leur titre. Les identifiants de médias sont générés à l'indexation et restent stables.

Les métadonnées enrichies (affiches, synopsis, notes) viennent des plugins — TMDB, OpenSubtitles. La bibliothèque core ne dépend d'aucune API externe.

API & Protocole

OpenAPI 3.0.3.
Une source de vérité.

Toutes les routes du serveur sont documentées dans un fichier openapi.yaml. C'est la source unique de vérité pour les clients officiels et les extensions tierces.

Les réponses d'erreur suivent un format JSON uniforme avec un code machine standardisé. Pas de messages d'erreur vagues ou variables selon la route.

Le dépôt norylum/protocol contient la spécification complète, les schémas JSON et les instructions de validation.

En cours — Acquisition V3

Le worker d'acquisition
est en construction.

Le système d'acquisition permet de demander du contenu depuis le serveur et de gérer son téléchargement via des sources autorisées. C'est une fonctionnalité avancée avec des contraintes de sécurité importantes.

Ce qui fonctionne : le cycle de vie des demandes (création, approbation, annulation), la file d'attente SQLite avec verrous immédiats, l'enregistrement des sources avec validation HTTPS et hash SHA-256.

Ce qui n'est pas encore activé : le téléchargement réseau réel, l'intégration Gluetun VPN, la recherche automatique de sources. Le worker tourne actuellement en mode --offline-smoke uniquement.
